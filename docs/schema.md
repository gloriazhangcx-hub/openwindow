# OpenWindow PostgreSQL schema

This document describes the Drizzle declarations in [`server/db/schema.ts`](../server/db/schema.ts). The schema stores per-user event snapshots and account data; public Discover listings currently come from the mock event source and are not automatically copied into accounts.

## Tables

| Table | Columns and constraints | Purpose |
|---|---|---|
| `users` | `id UUID` primary key, generated by default; `clerk_user_id VARCHAR(255)` required and unique; `email VARCHAR(320)` optional; `created_at TIMESTAMPTZ` required, defaults to the current time. | Maps a verified Clerk identity to OpenWindow's internal user row. |
| `events` | `id UUID` primary key; `user_id UUID` required, references `users.id` with delete cascade; optional `source_event_id VARCHAR(180)` and `legacy_event_id VARCHAR(180)`; required `title VARCHAR(240)`, `description TEXT`, `starts_at TIMESTAMPTZ`, `ends_at TIMESTAMPTZ`, `time_zone VARCHAR(100)`, `city VARCHAR(120)`, `venue VARCHAR(240)`, `source VARCHAR(20)`, `luma_url TEXT`; `created_at TIMESTAMPTZ` required, defaults to the current time. Unique index on (`user_id`, `legacy_event_id`) and an index on `user_id`. | User-owned snapshots of discovered events that are starred, rather than a shared public event catalog. |
| `event_topics` | `event_id UUID` required, references `events.id` with delete cascade; `topic VARCHAR(80)` required; composite primary key (`event_id`, `topic`). | Stores multiple topic labels per event. Topic values are stored directly; there is no separate topics lookup table. |
| `event_formats` | `event_id UUID` required, references `events.id` with delete cascade; `format VARCHAR(80)` required; composite primary key (`event_id`, `format`). | Stores multiple format labels per event. Format values are stored directly; there is no separate formats lookup table. |
| `stars` | `user_id UUID` and `event_id UUID` required, each with a foreign key that cascades on delete; `created_at TIMESTAMPTZ` required, defaults to the current time; `attendance_status VARCHAR(32)` required, defaults to `interested`, and is checked against `interested`, `planning_to_attend`, and `registered`. Composite primary key (`user_id`, `event_id`) and index on `user_id`. | The active user–event Star relationship used by the Star action and the Discover-event portion of My Events. Attendance status for a starred event lives on this relationship. |
| `saved_events` | Same relationship keys, timestamp, and attendance-status values as `stars`; composite primary key (`user_id`, `event_id`) and index on `user_id`. | A compatibility table retained for data-preserving migration from earlier Save/Star versions. Current account reads and Star writes use `stars`; migration code copies legacy rows between the tables idempotently and does not silently overwrite conflicting attendance statuses. It is not a second user-facing collection. |
| `manual_events` | `id UUID` primary key; `user_id UUID` required, references `users.id` with delete cascade; required `title VARCHAR(240)`, `description TEXT` (defaults to empty), `starts_at` / `ends_at TIMESTAMPTZ`, `time_zone VARCHAR(100)`, `location VARCHAR(240)` (defaults to empty), `event_url VARCHAR(2000)` (defaults to empty), `topics JSONB` and `formats JSONB` arrays (default to empty arrays), `attendance_status VARCHAR(32)` (defaults to `interested` and checked against the three supported values), and `created_at` / `updated_at TIMESTAMPTZ` (default to the current time). Check constraint requires `ends_at > starts_at`; index on (`user_id`, `starts_at`). | User-created events. They appear in My Events independently of starring and are not deleted when a user unstars a discovered event. |
| `busy_intervals` | `id UUID` primary key; `user_id UUID` required, references `users.id` with delete cascade; `legacy_key VARCHAR(64)` required; `starts_at` / `ends_at TIMESTAMPTZ` required; optional `time_zone VARCHAR(100)` and `source_id VARCHAR(80)`; `created_at TIMESTAMPTZ` required, defaults to the current time. Unique index on (`user_id`, `legacy_key`) and index on `user_id`. | Account-owned busy time used for conflict detection. It stores times and optional source identifiers, not calendar event titles or notes. |
| `user_preferences` | `user_id UUID` primary key and foreign key to `users.id` with delete cascade; required `preferences JSONB`; `updated_at TIMESTAMPTZ` required, defaults to the current time. | One preferences document per user. |
| `migration_snapshots` | `user_id UUID` primary key and foreign key to `users.id` with delete cascade; required `raw_payload JSONB`; `created_at TIMESTAMPTZ` required, defaults to the current time. | Preserves raw legacy browser-storage values associated with the account migration. |
| `openwindow_schema_migrations` | `id VARCHAR(120)` primary key; `applied_at TIMESTAMPTZ` defaults to the current time. | Records application-level data migrations so they can be applied idempotently. |

## Ownership and relationships

The Express account router obtains the account identity from the verified Clerk session. The server resolves that Clerk ID to `users.id`; private reads and writes use that internal ID rather than trusting a browser-supplied user ID. Event snapshots, stars, manual events, preferences, and busy intervals are scoped to that account.

`stars.user_id` and `stars.event_id` each have foreign keys, but the schema does not define a composite foreign key that enforces matching owners between a star and its event. The account store checks both the relationship's user ID and the event's user ID when reading or writing a star. The same server-side ownership rule applies to manual-event operations.

## Save and Star compatibility

The current UI has one Star action and uses `stars` for starred Discover events in My Events. `saved_events` remains in the database to preserve legacy rows during migration. The data migration checks for conflicting attendance values, uses conflict-safe inserts, records migration IDs, and retains the legacy relationship rows. Manual events use their own table and attendance column; they are not represented by `stars`.

## Schema and migration sources

- Drizzle table declarations: `server/db/schema.ts`
- Drizzle configuration: `drizzle.config.ts`
- Initial SQL migration: `drizzle/0000_add_manual_events.sql`
- Compatibility/data migration code: `server/db/legacy-star-migration.ts`, `server/db/saved-events-to-stars-migration.ts`, and `server/db/migrate-saved-events.ts`

Use the development database for development and tests. Do not point local tests or schema tooling at production. A documentation update does not require a database migration.
